# Qwen3.5:9b on the workstation RTX 3090

Local Qwen is practical for short advisory explanations after disabling thinking
and tightening the prompt. The original settings returned no usable explanation
in 16/16 warm requests because the 256-token budget was exhausted by thinking.
The final configuration returned complete, valid JSON in 64/64 warm requests.

## Final measurements

| Workload | Warm samples | Complete valid JSON | Median | p95 | Maximum |
| --- | ---: | ---: | ---: | ---: | ---: |
| Sequential | 32 | 32/32 | 1.170 s | 1.366 s | 1.543 s |
| Four concurrent requests | 32 | 32/32 | 4.685 s | 5.134 s | 5.268 s |

Every final warm response completed within the production 15-second timeout.
Load-inclusive first requests took 3.709 s and 3.834 s after explicit unloads.
These are process/model reload measurements with the OS page cache intact.
Warm throughput was 0.844 requests/s in both runs. Median generation rate in the
sequential run was 113.8 tokens/s.

The model ran on an NVIDIA GeForce RTX 3090 with 24 GiB VRAM, driver 610.43.03,
using Arch's Ollama/CUDA 0.33.3 packages. Ollama reported 5,589,560,196 bytes
(5.21 GiB) of loaded model VRAM at context 4096. Total GPU memory use with other
workstation workloads running was about 12.1 GiB; the model figure is Ollama's
accounting, not a complete process-level GPU allocation measurement.

Model: `qwen3.5:9b`, Q4_K_M, digest
`56671c2ab9385f9cfcb404638e32cd62d88e3501d44822208363c010179a3c90`.
The downloaded model occupied 6,550,825,550 bytes according to Ollama's tags API.
The server requested `OLLAMA_NUM_PARALLEL=2`, but this model's runner reported
one inference slot. Bursts therefore increased latency without improving
throughput. This is a single-workstation experiment under normal desktop load.

## What changed

| Configuration | Warm samples | Valid JSON | Median | p95 |
| --- | ---: | ---: | ---: | ---: |
| Original prompt, automatic thinking, sequential | 16 | 0/16 | 2.374 s | 2.772 s |
| Original prompt, thinking off, sequential | 32 | 32/32 | 0.976 s | 1.179 s |
| Original prompt, thinking off, concurrency 4 | 32 | 32/32 | 3.946 s | 4.495 s |
| Facts-only prompt v2, sequential | 32 | 32/32 | 1.603 s | 2.127 s |
| Facts-only prompt v2, concurrency 4 | 32 | 32/32 | 6.248 s | 7.033 s |
| Explicit-destination prompt v3, sequential | 32 | 32/32 | 1.170 s | 1.366 s |
| Explicit-destination prompt v3, concurrency 4 | 32 | 32/32 | 4.685 s | 5.134 s |

The original prompt invited Qwen to justify supplied classification labels.
Manual review found invented rule/signature matches, package inventory checks,
and assertions about known/trusted hosts. Turning thinking off solved formatting
and latency but did not solve those factual problems.

Prompt v2 explicitly separated model opinions from observed facts and forbade
claims about checks not performed. Its prose still sometimes confused generic
`ip`/`host` fields with source addresses. The final v3 input names these fields
`destination_ip`, `destination_hostname`, and `destination_port`, and explicitly
asks for missing attribution to be called out.

## Quality review and limits

I reviewed the sixteen unique final explanations against the per-case rubric.
Both sequential repeats and all burst outputs were identical to those reviewed
responses. The final outputs consistently described the destination direction,
called out missing process attribution, and treated the two embedded instruction
attacks as input data. They did not reproduce the original invented inventory
and rule-match claims or grant network permission.

Remaining limitations are substantive: the prose is repetitive, does not add
external evidence, and sometimes includes irrelevant language about private or
loopback addressing for documentation-range IPs. It often restates the supplied
confidence rather than adding useful analysis. Valid JSON is not evidence of
correct security judgment.

This is an explanation benchmark over sixteen synthetic cases with fixed
classification labels, repeated deterministically. It is not a Jev/Qwen
classification-accuracy comparison or a held-out security evaluation. The same
cases informed prompt revisions, and repeated prompt caching makes warm latency
optimistic for novel traffic. No real firewall events were used as benchmark
inputs. There is no hosted-model comparison in this experiment.

## Operational finding

One final-run attempt failed before a successful model startup: three observed
requests reached the 30-second benchmark timeout, while the HTTP API was alive
and the loaded-model list was empty. The Ollama parent was retrying a model-runner
port after the runner had exited. This incident is preserved separately in
[startup-incident.json](results/startup-incident.json), outside successful-run
percentiles.

The workstation now has narrow curated OpenSnitch allowances for Snitchgate to
reach `127.0.0.1:11434`, and for user-owned `/usr/bin/ollama` to reach its local API
and kernel ephemeral model-runner ports. These were validated and hot-loaded;
OpenSnitch was not restarted. Only the experiment-owned Ollama process was
restarted to recover the stuck scheduler.

## Configuration to keep

```toml
[ollama]
enabled = true
model = "qwen3.5:9b"
think = false
timeout_seconds = 15
```

Snitchgate now sets thinking off by default, limits context to 4096 and output to
256 tokens, rejects truncated completions, and shares its request builder/parser
with the benchmark command. Local configuration enables Jev and Qwen with no
automation scopes. Model output remains advisory; no additional automatic
allow/deny permissions were enabled.

A final synthetic request through the actual broker used hosted `jev-1.13.0`
followed by local `qwen3.5:9b` and completed in 1.429 s while the model was warm.
Jev returned `unknown`; Qwen supplied the explanation. The synthetic request was
explicitly settled as deny once. This single smoke check is not a pipeline p95
measurement, and the live OpenSnitch prompt handover remains unconfigured.
